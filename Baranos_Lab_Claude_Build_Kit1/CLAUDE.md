# Project instructions

Build **Baranos Lab: The Verification Files** according to `docs/BUILD_SPEC.md` and `docs/CASEBOOK.md`. Read `docs/SOURCES.md` before writing factual project explanations. Execute only the stage requested in the current prompt, completing that stage rather than stopping at a plan.

## Product intent

- Audience: Fogo community members, including beginners.
- Format: investigative missions connected by a fictional story. Each case has a decision, consequence and explanation.
- Learning precedes wallet connection. Technical depth is available through optional explanations and source references.
- Visual reference: supplied Baranos logo and whitepaper. Use the palette and typography in the build specification.
- Preserve the supplied logo's proportions, pixels and background. Do not trace, redraw, recolor or invent alternate marks. Use a CSS-sized image.

## Accuracy

- Treat the casebook's named characters, calculations, incident and model as fictional teaching devices.
- Distinguish a learning simulation, our learning program on Fogo testnet, and an actual Baranos job.
- A matching hash binds data; it does not prove inference was performed correctly. Our toy arithmetic exercise is not a Baranos verifier or an LLM.
- Execution integrity does not guarantee factual truth or sound judgment.
- Keep project targets separate from measured results. Never invent SDK imports, program IDs, transaction hashes, benchmark numbers or team endorsement.
- If an integration detail is missing, leave the live feature unavailable with a useful explanation and record the dependency. Complete unrelated authorized work.

## Implementation

- Use React, TypeScript, Vite and scoped CSS for the new frontend. Choose compatible current stable dependencies, commit a lockfile, and document the Node version actually tested.
- Store mission content separately from React components. Use pure functions for the toy model, transitions and local feedback.
- Preserve guest progress with schema versioning and recover gracefully from invalid storage.
- Treat all browser-supplied scores and completion flags as untrusted for the onchain release.
- Use native, keyboard-accessible controls, visible focus and tap-friendly targets. Honor reduced motion. Provide click/tap alternatives to dragging.
- Keep secrets in server-side configuration; no secrets in `VITE_` variables, repository files, logs or chat messages.
- Use minimal tests that exercise learning outcomes, transitions, storage recovery and, when introduced, authorization and transaction failures.

## Delivery

For each stage report: what runs, what is simulated, commands executed with outcomes, unresolved dependencies and exact files changed. Provide screenshots when browser tools are available; disclose if visual testing could not run. Prepare changes in a reviewable branch. Do not claim a deployment occurred without a real URL or verified chain transaction.
